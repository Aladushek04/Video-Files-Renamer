# PHASH: поиск сцен в StashDB по перцептивному хэшу — дизайн

Дата: 2026-11-05
Статус: одобрен пользователем 2026-11-05, поиск по всем трём источникам. Следующий шаг — план реализации
Проект: `video_renamer`

## Интент

Сейчас OSHASH находит только точные копии файла. Перекодированная версия
(другой битрейт, контейнер, кодек) получает другой OSHASH и не находится по
отпечатку, остаётся только текстовый поиск. Это главный пробел из раздела
«Известные ограничения» CHANGELOG и «Риски» в `docs/architecture.md`.

Цель: добавить второй отпечаток — PHASH, совместимый со Stash/StashDB. Файлы,
для которых OSHASH ничего не дал, получают попытку поиска по PHASH. Найденная
по PHASH сцена всегда уходит на ревью человеку.

## Источники фингерпринтов

Решение пользователя: OSHASH и PHASH ищутся одновременно в StashDB,
ThePornDB и FansDB. Текстовый поиск остаётся только в StashDB (решение
строителя: текст не расширяем, пока не проверено качество данных вторых
источников).

Эндпоинты и ключи — те же, что у скраперов студий (`video_renamer/scrapers/stashdb.py`):

| Источник | Эндпоинт | Ключ в `.env` |
|---|---|---|
| StashDB | `https://stashdb.org/graphql` | `STASHDB_API_KEY` |
| ThePornDB | `https://theporndb.net/graphql` | `THE_PORNDB_API_KEY` |
| FansDB | `https://fansdb.cc/graphql` | `FANSDB_API_KEY` |

Правила:

- Порядок источников: StashDB, ThePornDB, FansDB. Порядок задаёт приоритет при
  выборе между одинаковыми сценами.
- Каждая сцена получает поле `source` (`StashDB`, `ThePornDB`, `FansDB`).
  Значение по умолчанию — `StashDB`, чтобы старый код и кэш не ломались.
- Для каждого файла собирается объединённый список сцен со всех источников.
- Дубликаты: две сцены одна и та же, если совпадают нормализованные название
  (`normalize_for_match`), дата выпуска и студия. Из дубликатов остаётся
  сцена с более высоким приоритетом источника.
- Автоодобрение OSHASH (`approved=y`): только если после дедупликации одна
  сцена и её итоговое имя валидно, как и раньше. Если сцен несколько —
  `approved=n`, все перечисляются в `note` с указанием источника.
- PHASH: `approved=n` всегда, как и было решено.
- Ошибки источников:
  - StashDB: как сейчас. Неверный ключ — фатально для preview; временная
    ошибка — `stashdb_error` и код возврата 1.
  - ThePornDB и FansDB: отсутствие ключа, неверный ключ и временная ошибка
    превращаются в предупреждение в `warnings`. Остальные источники работают.
    В `note` строки добавляется `<Источник>_error`, код возврата 1 только при
    временной ошибке.
- Кэш: новая таблица `fingerprint_cache(source TEXT, algorithm TEXT,
  hash TEXT, scenes TEXT, fetched_at TEXT, PRIMARY KEY (source, algorithm,
  hash))`. Существующие записи `fingerprints` однократно переносятся в неё как
  `('StashDB', 'OSHASH', hash)`. Старая таблица больше не читается.
- `phash_fingerprints` из раздела «Компоненты» заменяется той же
  `fingerprint_cache` с `algorithm = 'PHASH'`. Таблица `local_phash`
  остаётся.
- Сеть: отдельный клиент и своя пауза на каждый источник, батчи по 40.
- `offline`: читается кэш всех источников. Сеть запрещена для всех.
- Ключи загружаются тем же способом, что и `STASHDB_API_KEY` (`load_project_env`).

## Цели

- Считать PHASH тем же алгоритмом, что Stash (`pkg/hash/videophash`), чтобы
  хэши совпадали с сохранёнными в StashDB (с допуском до 4 бит).
- Искать по PHASH батчами через `findScenesBySceneFingerprints` с
  `algorithm: PHASH`.
- Совпадение по PHASH: `source=phash`, `approved=n` всегда. Автоматического
  применения нет.
- Не менять поведение `apply`, форматы CSV и существующие проверки
  устаревания (размер + OSHASH).
- Работать на Windows без pip-зависимостей: только stdlib и внешние
  `ffmpeg`/`ffprobe`.

## Анти-цели

- Не одобрять PHASH-совпадение автоматически, даже при одной сцене.
- Не считать PHASH для файлов, у которых уже есть OSHASH-совпадение.
- Не строить собственный перцептивный хэш, несовместимый со StashDB.
- Не добавлять внешние pip-пакеты (`imagehash`, `PyAV`, `numpy`, `opencv`).
- Не запускать ffmpeg через оболочку (shell) и не передавать путь строкой.

## Ограничения

- ffmpeg/ffprobe установлены через winget, но в PATH не попадают. CLI
  принимает пути явно (`--ffmpeg`, `--ffprobe`) или через переменные
  окружения `FFMPEG_PATH`/`FFPROBE_PATH`.
- Порог StashDB: расстояние до 4 бит включительно (проба). Запас у нашей
  реализации — 2 бита.
- Нагрузка: 4–11 с на файл. Для больших папок это заметно.
- Доля файлов, которые PHASH найдёт сверх OSHASH, пока не измерена (см.
  «Открытые вопросы»).

## Подходы

Рассматривались три варианта:

1. **Совместимость со Stash (выбран).** ffprobe даёт длительность, затем 25
   вызовов ffmpeg с быстрым seek, масштаб до 160 px и вывод кадров в BMP.
   Python собирает сетку 5×5 и считает `PerceptionHash`. Хэши совпадают с
   StashDB с расстоянием 0–2 бита.
2. Гибрид: фильтр ffmpeg `tile=5x5` собирает сетку, Python только считает
   хэш. Меньше кода на Python, но выбор кадров по таймкодам через `select`
   неудобен, а пиксели отличаются от Stash. Отвергнут.
3. Собственный перцептивный хэш или внешние библиотеки. Хэш не совпадёт со
   StashDB, поэтому поиска не будет. Библиотеки нарушают правило «без
   обязательных pip-зависимостей». Отвергнут.

Выбран вариант 1. Одобрен пользователем.

## Алгоритм PHASH

Из `pkg/hash/videophash/phash.go` (ветка `develop`, сверено 2026-11-05):

- Кадры: `t_i = 0.05·D + i·(0.9·D / 25)`, `i = 0..24`, где `D` — длительность
  файла в секундах (ffprobe, `format=duration`).
- Каждый кадр: ffmpeg с `-ss` до `-i` (быстрый seek), один кадр
  (`-frames:v 1`), фильтр `scale=160:-2`, вывод BMP. Если быстрый seek
  завершился ошибкой, для этого и всех следующих кадров файла Stash переходит
  на точный seek (`-ss` после `-i`). Повторяем.
- Сетка: 5 колонок × 5 строк; кадр `i` вставляется в
  `(w·(i mod 5), h·floor(i / 5))`, размер ячейки берётся из первого кадра.

Из `corona10/goimagehash` (`hashcompute.go`, `transforms/`, `etcs/`; сверено):

- `PerceptionHash`: масштабирование до 64×64 (`nfnt/resize`, `Bilinear`),
  перевод в серый, DCT-II (без нормировки) по строкам и столбцам, берутся
  только коэффициенты 8×8 (`flattens[8*j+i]`).
- Медиана: quickselect по 64 значениям, для чётной длины — среднее двух
  средних элементов (`seq[k-1]/2 + seq[k]/2`, `k = 32`).
- Бит `idx` ставится при `p > median`, позиция бита `63 - idx`.
- Значение — 64 бита, в StashDB хранится как 16 hex-символов.

Серый: `0.299·R + 0.587·G + 0.114·B` по 8-битным значениям (проверено на
соответствии StashDB).

Ресемплинг: `nfnt/resize` использует 8-битные целочисленные веса фильтра,
которые здесь не воспроизведены побитово. Пробная реализация использует
треугольный фильтр с тем же масштабом. Результат совпадает с StashDB в
пределах 0–2 бит, это достаточно для порога 4.

## Компоненты

### `video_renamer/core/phash.py` (новый)

- `probe_duration(path, ffprobe) -> float` — `ffprobe` с `-show_entries
  format=duration`. Ошибка, если `D <= 0`.
- `frame_times(duration) -> list[float]` — 25 отметок по формуле выше.
- `extract_frame(path, t, *, accurate, ffmpeg) -> bytes` — один вызов ffmpeg,
  аргументы списком, путь абсолютный.
- `decode_bmp(data) -> (width, height, gray_rows)` — 24/32-bit BMP на stdlib
  (`struct`), выравнивание строк 4 байта, ориентация снизу вверх или сверху
  вниз.
- `build_montage(frames) -> gray_rows` — сетка 5×5.
- `resize_bilinear(gray, 64, 64)` — ресемплинг.
- `dct_top_left_8x8(pixels64) -> list[float]` — вычисляется только левый
  верхний блок 8×8, около 36 тысяч умножений.
- `quick_select_median(seq, 0, 63, 32)` — порт из goimagehash.
- `phash_from_path(path, *, ffmpeg, ffprobe) -> int` — полный конвейер.
- `class PhashError(ValueError)` — ошибка файла (нет длительности, ffmpeg
  не вернул кадр, неподдерживаемый BMP).
- `class PhashToolError(RuntimeError)` — ffmpeg/ffprobe не найдены или не
  запускаются. CLI проверяет их до обхода файлов, если включён `--phash`.

### `stashdb_client.py`

- `find_scenes_by_hashes(hashes, algorithm="OSHASH")` — параметр алгоритма
  в `{"hash": h, "algorithm": algorithm}`. Вызов без аргумента работает как
  раньше.
- Тесты: батч до 40, выравнивание ответа, `algorithm` попадает в запрос.

### `title_cache.py`

- Новая таблица `phash_fingerprints(hash TEXT PRIMARY KEY, scenes TEXT NOT
  NULL, fetched_at TEXT NOT NULL)`. Существующая `fingerprints` не меняется,
  миграция не нужна.
- Методы `get_phash_fingerprint(hash)` и `put_phash_fingerprint(hash, scenes)`
  с TTL 30 дней и отрицательным кэшем (`[]`), как у OSHASH.
- Новая таблица `local_phash(oshash TEXT, size INTEGER, phash TEXT NOT NULL,
  computed_at TEXT NOT NULL, PRIMARY KEY (oshash, size))`. Ключ — содержимое
  файла, а не путь. Повторный preview не декодирует видео заново. TTL нет:
  хэш файла не меняется.

### `title_matcher.py`

- `resolve_match(local, studios, fingerprint_scenes, text_scenes,
  phash_scenes=())`. Новый параметр по умолчанию пустой, старые вызовы не
  меняются.
- Если `fingerprint_scenes` пуст и `phash_scenes` непуст, возвращается
  `MatchResult(source="phash", approved=False, ...)`:
  - одна сцена: `scene` = она, `confidence` = 0.9 (см. «Решения строителя»),
    `new_stem` собирается через `build_scene_stem`, если валидно, иначе
    эвристика;
  - несколько сцен: `scene` = первая по порядку StashDB, все перечислены в
    `candidates`, в `note` — их список.
  - В `note` всегда указывается, что это совпадение по PHASH и требует ревью.
- Текстовый поиск пропускается, если найдено хотя бы одно PHASH-совпадение.

### `title_service.py`

- Новые параметры `phash: bool = False` и `phash_func` (по умолчанию
  `phash_from_path`), по образцу `oshash_func`, чтобы тесты не запускали
  ffmpeg.
- Новый этап `_resolve_phash` между `_resolve_fingerprints` и `_resolve_text`:
  - только кандидаты без `fingerprint_scenes`;
  - сначала `local_phash` по `(oshash, size)`, потом `phash_fingerprints` по
    хэшу, потом сеть;
  - вычисленный PHASH и сетевой ответ сохраняются в кэш;
  - ошибка ffmpeg на файле — предупреждение `phash error: ...` в `note`, файл
    идёт дальше к тексту; это не `stashdb_error`;
  - временная ошибка StashDB — `stashdb_error`, как у OSHASH.
- Прогресс: новая фаза `phash` (`current`/`total` — число файлов).
- `offline` запрещает сеть, но читает кэш. `refresh` игнорирует кэш StashDB,
  но не `local_phash` (он не зависит от StashDB).
- `apply_rows` не меняется: проверка устаревания — размер и OSHASH. PHASH в
  CSV не сохраняется, чтобы apply не декодировал видео.

### CLI (`video_renamer/cli.py`, `fix_video_titles.py`)

- Флаг `--phash` для `preview`, по умолчанию выключен.
- Флаги `--ffmpeg PATH` и `--ffprobe PATH`, или переменные окружения
  `FFMPEG_PATH`/`FFPROBE_PATH`. Без них — поиск в PATH.
- Проверка инструментов при старте, если `--phash` задан.

### TUI

- `tui_model.py`: добавить источник `phash` в список и счётчики (иначе
  счётчики по источникам не покрывают новое значение).
- `tui.py`: метка «PHASH», цвет, подпись источника и фазы `phash`

- Включение PHASH в TUI — отдельная задача после приёмки CLI.

## Решения строителя (мои, можно изменить)

- Флаг `--phash` выключен по умолчанию из-за нагрузки на CPU.
- PHASH вызывается только для файлов без OSHASH-совпадения.
- Хранение: отдельные таблицы `phash_fingerprints` и `local_phash`,
  существующая `fingerprints` не трогается.
- `confidence` для PHASH = 0.9 (не 1.0 — это точное совпадение). Можно
  выводить из расстояния, но StashDB возвращает сцену без расстояния.
- Текстовый этап пропускается для файлов с PHASH-совпадением, как и для
  OSHASH. Если PHASH ничего не дал, текст работает как раньше.
- Ресемплинг: треугольный фильтр (проба: 0–2 бита). Точная копия весов
  `nfnt/resize` — только если тесты покажут дрейф больше 2 бит.
- Версия Stash: ветка `develop`, сверено 2026-11-05. При реализации
  зафиксировать коммит.

## Открытые вопросы

1. Нужен ли замер на остальных 67 файлах (ориентировочно 10–15 минут CPU, только
   чтение StashDB)? Он покажет, сколько дополнительных сцен даст PHASH в вашей
   папке.
Решено пользователем: документ одобрен, фингерпринты ищутся во всех трёх
источниках (см. «Источники фингерпринтов»). Замер PHASH на оставшихся 67 файлах
не выполнялся; он не нужен для реализации, но даёт оценку пользы. Может
выполняться после реализации на реальной папке.

Закрыто пробой: порог StashDB (4 бита), эталон (сохранённые PHASH в StashDB),
расположение ffmpeg (winget), совместимость алгоритма (0–2 бита на 16 файлах).

## Что не входит в объём

- Автоматическое одобрение PHASH-совпадений.
- Поиск по расстоянию Хэмминга в локальной базе.
- Изменение логики `apply`.
- Выбор кандидатов в TUI (уже есть отдельно, не меняется).
- Перенос PHASH в метаданные файла.
