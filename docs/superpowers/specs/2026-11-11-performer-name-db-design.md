# База имён исполнителей из StashDB — исследование и дизайн

Дата: 2026-11-11
Статус: реализовано (справочник, скрейпер, интеграция, тесты)
Проект: `video_renamer`

## Интент

Переименователю нужен локальный справочник имён актёров и актрис, чтобы
узнавать имена в имени файла, отделять их от названия, корректно считать
сходство и работать без сети. Предлагалось два источника:

1. скрейп StashDB (только он);
2. готовая база face-recognition в `G:\Projects\FaceService\actors`.

Ниже — проверенные факты, оценка обоих источников и дизайн, если делать.

## Вердикт

- Скрейп StashDB через GraphQL **осуществим и дёшев**: 114 769 исполнителей,
  115 запросов по 1000 строк, 2,5–3,5 минуты, без 429 и без потерь.
- **FaceService как источник имён не нужен.** Его 11 867 имён — почти точное
  подмножество StashDB: 11 866 записей совпадают по `stashdb_id`, расходятся
  одно устаревшее имя и одна удалённая/слитая запись. Своих имён база не
  добавляет; она полезна только как мост «лицо → `stashdb_id`», не как
  справочник.
- Для сопоставления в имени файла нужен **отдельный компактный индекс**
  (нормализованное имя/алиас → каноническое имя), а не полная база на 22 МБ.
  Индекс занимает 4,3 МБ и загружается за 0,18 с.
- Критично для скрейпера: пагинация **только `sort: NAME`**. Сортировка
  `CREATED_AT` даёт неустойчивые страницы: 8 177 записей теряются, 5 990 id
  повторяются.

## Проверено на живом StashDB

Дата проверки: 2026-11-11. Эндпоинт `https://stashdb.org/graphql`,
авторизация заголовком `ApiKey` (как в остальном проекте).

### Запрос и схема

`queryPerformers(input: PerformerQueryInput!)` существует и поддерживает
`page`, `per_page`, `sort`, `direction`. Поля `Performer`: `id`, `name`,
`aliases` (список строк), `gender`, `disambiguation`, `scene_count`,
`deleted`, `merged_into_id`, `updated`.

Рабочий запрос:

```graphql
query Performers($input: PerformerQueryInput!) {
  queryPerformers(input: $input) {
    count
    performers {
      id
      name
      aliases
      gender
      disambiguation
      scene_count
      deleted
      merged_into_id
      updated
    }
  }
}
```

Переменные страницы:

```json
{"input": {"page": 1, "per_page": 1000, "sort": "NAME", "direction": "ASC"}}
```

`per_page` 200, 500 и 1000 принимаются (проверено). `count` в ответе — общее
число записей, по нему надо контролировать полноту выгрузки.

### Объём и скорость

| Параметр | Значение |
|---|---|
| Всего исполнителей | 114 769 |
| Страниц по 1000 | 115 |
| Время полной выгрузки | 211,6 с (пауза 0,4 с) |
| Ошибки 429/5xx | нет |
| Повторы id при `sort: NAME` | 0 (два независимых прогона) |
| Повторы id при `sort: CREATED_AT` | 5 990 id, 8 177 лишних копий |
| Потеряно при `sort: CREATED_AT` | 8 177 (уникальных 106 592 из 114 769) |

Причина расхождения — неустойчивый порядок записей с одинаковым
`CREATED_AT`; при постраничной выборке границы страниц «съезжают». `NAME`
такой проблемы не показал. Скрапер обязан после выгрузки сверить
`len(unique_ids) == count` и предупредить, если не совпало.

Важно: нельзя останавливаться по условию `len(batch) < per_page`, если сервер
молча ограничит `per_page`. Цикл должен идти по `page`, пока не набрано
`count` или страница не пуста.

## Зачем справочник переименователю

Точные исполнители сцены уже приходят из StashDB; справочник их не заменяет.
Он закрывает случаи, где сцены нет или она не нашлась:

1. **Fallback-разбор имени (главная ценность).** Сейчас
   `split_actors_title` угадывает актёров по «два слова подряд» и путает
   название с именем. Справочник позволяет вырезать из остатка самые длинные
   известные имена: `Yasmina Khan - Manuel Ferrara Finally Got His Hands On
   Me` → актёры `Yasmina Khan`, `Manuel Ferrara`, название `Finally Got His
   Hands On Me`.
2. **Чистое сходство названий.** `_title_similarity` вычитает имена только
   исполнителей кандидата. Если в файле есть имя, которого у кандидата нет,
   оно остаётся в «названии» и занижает score. Справочник позволяет вычесть
   все известные имена из локального остатка.
3. **Второй текстовый запрос.** Если полный остаток не дал кандидата, можно
   повторить `searchScene` только по названию, без имён. Полный остаток уже
   работает (проверено на `yasmina khan manuel ferrara ...`), поэтому это
   запасной, а не основной путь.
4. **Подсказка по алиасу.** `Siri` → `Siri Dahl` для поискового запроса.
   Каноническое имя в итоговом имени не подменяет `as` из сцены.
5. **TUI: автодополнение и проверка** ручного имени (необязательно).
6. **Офлайн-режим:** разбор имён без сети.

Анти-цели:

- не подменять `performers[].as` / `performer.name` сцены данными справочника;
- не угадывать актёров по односложным именам и неоднозначным алиасам;
- не тянуть имена из FansDB/ThePornDB (только StashDB);
- не импортировать FaceService как второй источник.

### Найденный конфликт: студия съедает имя

Порядок старого конвейера — сначала `extract_studio`, потом актёры. Если первое
слово имени совпадает с названием студии, имя разваливается. В StashDB есть
студия `VERONICA`, поэтому файл
`veronica-leal-xxxx-i-tested-...` разбирался так:

```text
studio: VERONICA
rest: leal xxxx i tested some new dicks ...
heuristic: VERONICA - Leal Xxxx - I Tested Some New Dicks ...
```

Поэтому имена вырезаются до `extract_studio` (`prepare_stem_with_names`):
сначала находится `Veronica Leal`, её токены удаляются из строки, и только потом
ищется студия. Для настоящих студий поведение сохраняется: в
`Vrbangers - 22.12.2025 - Gabbie Carter - Title` студия и дата остаются на месте.

## Реализованный дизайн

### Артефакты

- `data/performers.json` — полная база для TUI и обновлений, 22 МБ;
- `data/performers_index.json` — компактный индекс для матчинга, 4,3 МБ;
- `scrape-performers` — точка входа рядом с `scrape-stashdb`.

Формат базы:

```json
{
  "source": "stashdb",
  "synced_at": "2026-11-11T00:00:00Z",
  "count": 114769,
  "performers": [
    {
      "id": "uuid",
      "name": "Yasmina Khan",
      "aliases": ["..."],
      "gender": "FEMALE",
      "disambiguation": null,
      "scene_count": 123,
      "updated": "2026-10-01T12:00:00Z"
    }
  ]
}
```

Формат индекса — плоский объект `{"yasmina khan": "Yasmina Khan", ...}`.
Индекс строится на выгрузке, а не в рантайме.

### Скрапер

Повторяет устройство `scrapers/stashdb.py`: страницы, checkpoint после каждой
страницы (только с `--apply`), атомарная запись, `.bak`, dry-run по умолчанию.
Отличия:

- `sort: NAME`, `direction: ASC`, `per_page: 1000`;
- цикл до `count`, а не до короткой страницы;
- после выгрузки — проверка `len(unique_ids) == count`; расхождение — ошибка
  или предупреждение с кодом возврата;
- дедупликация по `id` перед записью;
- индекс пишется тем же проходом.

Полное обновление занимает минуты, поэтому инкрементальный режим не нужен.
Фильтра `updated > ...` в `PerformerQueryInput` нет; `sort: UPDATED_AT` даст
те же неустойчивые страницы, что и `CREATED_AT`.

Ограничение: 1000 строк на страницу сейчас работает, но может быть понижено
на стороне сервера. При понижении цикл по `count` продолжит работу, просто
страниц станет больше.

### Индекс и правила сопоставления

- Нормализовать ключи `normalize_for_match`.
- Брать только ключи, которые указывают ровно на одно каноническое имя.
- Для назначения актёров — только многотокенные ключи (2–5 слов).
- Числовые и ключи короче 3 символов отбрасывать.
- Искать по границам токенов, самое длинное совпадение первым.
- Односложные имена (34 705) в первой версии не использовать: на примерах они
  дают `Porn`, `Hardcore`, `Glory`, `Brazilian` — это реальные имена или
  алиасы, но в имени файла они неотличимы от обычных слов.
- Неоднозначные многотокенные ключи (3 281 алиас) отбрасывать: `Colette`,
  `Zoe` и подобные указывают на десятки людей.

### Точки интеграции

- `video_renamer/paths.py`: `PERFORMERS_PATH`, `PERFORMERS_INDEX_PATH`.
- `core/performer_names.py`: `PerformerIndex.load()`, `find_names()`,
  `strip_names()`, `build_index()`.
- `clean_ph_names.prepare_stem_with_names(stem, studios, performers)` —
  вырезает имена до студии; `prepare_stem` остался трёхэлементным и без имён.
- `clean_ph_names.split_actors_title(rest, known_actors=())` — найденные имена
  становятся актёрами, остаток — названием.
- `title_matcher.LocalNameInfo`: поля `known_actors` и свойство `search_text`;
  `parse_local_name(..., performers=None)`.
- `title_matcher.build_heuristic_stem`: при `known_actors` собирает имя из
  студии, даты, имён и остатка без имён.
- `title_service.TitleService(..., performers=...)`; `_resolve_text` берёт
  `local.search_text`, поэтому в запрос попадают канонические имена.
- CLI: `--names` / `--no-names`; TUI: индекс подхватывается, если файл есть.

Второй текстовый запрос (только название) не понадобился: полный остаток с
каноническими именами уже даёт лучший запрос, чем прежний обрезанный.

## Риски и ограничения

- **Ложные срабатывания.** Даже многотокенные имена могут быть названием
  сцены. Поэтому справочник не должен автоматически одобрять строку: он
  только улучшает кандидатов и fallback, решение остаётся за ревью.
- **Односложные исполнители не покрыты** (30% базы). Это осознанное
  ограничение первой версии.
- **Устаревание.** Полное обновление — минуты, но запускать его надо вручную
  или по расписанию; `synced_at` в файле позволит показывать возраст.
- **Условия использования и лицензия данных.** Перед коммитом 22 МБ
  справочника в публичный репозиторий нужно проверить условия StashDB.
  В проекте уже лежит `data/studios.json` на 19 МБ, прецедент есть, но это
  не отменяет проверки.
- **Память.** Полная база с индексом в пике ~195 МБ; готовый индекс — ~31 МБ.
  На Windows-десктопе приемлемо, но индекс лучше грузить лениво.
- **Дубликаты и переименования в StashDB.** `merged_into_id` и `deleted`
  надо обрабатывать при обновлении; точечные удалённые записи через
  `queryPerformers` не видны.
- **Кодировка и Windows.** Имена содержат Unicode (в том числе CJK); запись
  в UTF-8 без `ensure_ascii` уже используется в проекте.
