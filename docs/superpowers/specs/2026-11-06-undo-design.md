# Откат уже выполненных переименований — дизайн

Дата: 2026-11-06
Статус: проверка строителем пройдена, ждёт решения по открытому вопросу и одобрения
Проект: `video_renamer`

## Интент

Архитектурный документ требует, чтобы журнал и откат были видны. Сейчас откат
есть только внутри одного `apply` при ошибке (`_rollback_apply_item`). Строки,
которые `apply` уже переименовал и записал в `rename_log.csv`, откатить нельзя.
Пользователь ошибся в одной строке или хочет вернуть один файл — приходится
переименовывать руками, а журнал ничего не подсказывает.

Цель: откат отдельных записанных строк журнала, из CLI и из TUI, с теми же
проверками безопасности, что у `apply`.

## Цели

- Показать активные (ещё не откатённые) строки журнала с идентификаторами.
- Откатить выбранные строки по идентификаторам. Без `--apply` — dry-run.
- Проверять каждую строку перед откатом: файл на новом пути есть, это обычный
  файл, его OSHASH совпадает с журналом (и размер, если он записан), исходное
  имя свободно. Цепочки имён обрабатываются так же, как в `apply`.
- Журнал не переписывается и не теряет строк: откат дописывается как новая
  запись, исходная остаётся.
- Журнал знает корневую папку каждой строки, чтобы откат не попал в другую папку.
- TUI: экран журнала с отметками строк, предпросмотр и подтверждение отката.

## Анти-цели

- Не откатывать строку без проверки OSHASH. Строку без OSHASH не откатываем.
- Не угадывать корневую папку для старых строк. Без явного `--root` их не
  откатываем.
- Не удалять и не переписывать строки журнала.
- Не откатывать уже откатённую строку повторно.
- Не откатывать файлы, которые были удалены или переименованы вне `apply`.
- Не откатывать откат (повтор переименования — отдельная задача).

## Ограничения

- `rename_log.csv` сейчас пишется в `LOG_PATH` (корень проекта) один на все
  папки. Пути в нём относительные (`old`, `new`), корень не записан.
- Текущий формат: `timestamp;old;new;oshash;scene_id;source` (6 колонок).
  Размер файла в журнале не записывается.
- В журнале уже могут быть строки старого формата; их нельзя потерять.
- CLI пишет метку времени в формате `%Y-%m-%dT%H:%M:%SZ`, TUI — в `isoformat()`.
  Идентификатор запуска (общая метка времени строк одного `apply`) сейчас
  неодинаков по формату. Нужен один формат.
- Windows: файлы могут быть открыты в другой программе, переименование может
  не сработать. Ошибка по строке не должна останавливать откат остальных.

## Подходы

Рассматривались три варианта. Выбран вариант A (пользователь, 2026-11-06).

1. **A. Журнал дописывается, откат — новой записью (выбран).** Колонка
   `action` (`rename` / `undo`), колонка `undoes` у записи отката ссылается на
   идентификатор отменённой строки. Состояние строки вычисляется при чтении.
2. Переписать журнал без отменённых строк. Отвергнут: теряет историю,
   нарушает «журнал виден», рискован при открытом в Excel файле.
3. Отдельный `undo_log.csv`. Отвергнут: два файла нужно сверять, расхождения
   неизбежны.

## Формат журнала

Новый формат (заголовок пишется один раз, в начале файла):

```
timestamp;action;undoes;root;old;new;oshash;size;scene_id;source
```

- `timestamp` — метка одного запуска (UTC, `%Y-%m-%dT%H:%M:%S.%fZ`, с
  микросекундами), общая для всех строк запуска `apply` и отката. Микросекунды
  нужны, чтобы два запуска в одну секунду (например `A→B`, откат, снова `A→B`)
  не получили одинаковый `id`. Этот формат — единственный и для CLI, и для TUI.
- `action` — `rename` или `undo`.
- `undoes` — пусто для `rename`; для `undo` — идентификатор отменённой строки.
- `root` — абсолютный путь корневой папки (`os.path.abspath`).
- `old`, `new` — пути относительно `root`, как сейчас.
- `oshash`, `size` — из `PreviewRow`; `size` может быть пустым (старые строки).
- `scene_id`, `source` — как сейчас.

Идентификатор строки (`id`) не хранится, а вычисляется как первые 10
hex-символов SHA-1 от `timestamp|action|root|old|new`. Он стабилен и виден в
`undo --list`. Для строк старого формата `root` пуст.

Старый файл `rename_log.csv` в старом формате не дописывается новыми колонками.
Старый формат распознаётся по заголовку (ровно `timestamp;old;new;oshash;scene_id;source`).
Перед первой записью в новом формате такой файл переименовывается в
`rename_log.legacy.csv` (если он уже существует, добавляется суффикс с датой).
Если переименование не удалось, запись прерывается с ошибкой (код 2): смешанный
формат в одном файле недопустим. Новый `rename_log.csv` начинается с нового
заголовка. Чтение учитывает оба файла. Файл, переданный через `--log PATH`,
мигрируется по тем же правилам: legacy-копия создаётся рядом с ним.

## Состояние строки

Строка `rename` активна, если нет записи `undo`, у которой `undoes` равен её
`id`. Записи `undo` сами не отображаются в списке активных. Одна строка
откатывается не более одного раза.

## Откат: алгоритм

Вход: список идентификаторов, корень (для старых строк — из `--root`), флаг
применения. Для каждого идентификатора:

1. Строка должна существовать и быть активной. Иначе ошибка строки, остальные
   продолжаются.
2. Для строки с `root` используется этот корень. Для строки без `root` нужен
   `--root`; если его нет — ошибка строки.
3. Проверки (как в `apply`): путь внутри корня, без symlink/junction, обычный
   файл; OSHASH совпадает; если `size` записан — совпадает и он.
4. Откат — двухфазное переименование `new → old`. Для этого `TitleService`
   получает отдельный метод `undo_rows(rows, dry_run)`, который переиспользует
   `_prepare_apply_item`, `_resolve_apply_target` и двухфазную логику `apply_rows`.
   Строки для отката строятся как `PreviewRow(approved=True, old_rel=new,
   new_rel=old, ...)`.
5. Успешно откатённые строки дописываются в журнал как `undo`, `undoes` =
   id исходной строки. Ошибочные — не пишутся.
   Если файл откатён, а запись в журнал не удалась (например, журнал открыт в
   Excel), строка получает статус «откат выполнен, журнал не записан» с
   идентификатором. Автоматического повтора нет: повторный откат такой строки
   упёрся бы в занятое имя, и пользователь должен решить сам. Код возврата 1.

Порядок и цепочки: как в `apply` (заблокированные строки не входят в
первую фазу, их old-путь остаётся занятым).

Если откат части строк не прошёл, уже откатённые остаются откатёнными и
записаны в журнал. Частичный откат не отменяется.

## Изменения в проверках

`PreviewRow.size` сейчас `int`, и `_prepare_apply_item` сравнивает его всегда.
Для строк без размера (старый журнал) проверка размера пропускается, проверка
OSHASH остаётся. Тип меняется на `int | None`, `None` означает «не записан».
Поведение `apply` для строк с размером не меняется.

Чтение размера из журнала отдельное: пустая ячейка становится `None`. Чтение
`preview.csv` (`_parse_int`, пустое → `0`) не меняется, чтобы не изменить
поведение `apply` для существующих CSV. Запись `None` в журнал — пустая ячейка,
не `"None"`.

## CLI

```text
video-renamer undo --list [--log PATH] [--root PATH]
video-renamer undo --ids ID[,ID...] [--log PATH] [--root PATH] [--apply]
```

- `--list`: печатает активные строки: `id`, `old` → `new`, `root`, `timestamp`.
  Строки старого формата выводятся с пустым `root`.
- `--ids`: откатывает выбранные идентификаторы. Без `--apply` — dry-run:
  печатает план и ничего не меняет.
- `--root`: нужен только для строк старого формата.
- Код возврата: 0 — всё откатано или dry-run без ошибок; 1 — были ошибки
  строк; 2 — неверные аргументы или нечитаемый журнал.

Метка времени для CLI и TUI — одна функция (`_timestamp()`), TUI перестаёт
использовать `isoformat()`.

## TUI

- Новый экран «Журнал» (клавиша `u` на экране ревью, и `Esc` возвращает).
- Таблица активных строк: отметка пробелом, идентификатор, `old → new`,
  корень, время.
- Кнопка «Откатить выбранные» открывает подтверждение с предпросмотром
  (dry-run): что вернётся на место и что будет пропущено.
- Откат выполняется в фоне, как `apply`, результат показывается с числом
  откатённых и ошибками.
- Логика вне Textual: список и состояние строк берутся из модуля журнала
  (`video_renamer/core/rename_log.py`), TUI не парсит CSV сам.
- Экран читает `LOG_PATH` (тот же файл, куда пишет `apply`), а не
  `rename_log.csv` относительно текущей папки. Поле `log_path` экрана служит
  только для отображения.

## Решения строителя (мои, можно изменить)

- Идентификатор — хэш от полей строки, а не номер строки (номер меняется при
  дописывании).
- Старый журнал переименовывается в `rename_log.legacy.csv`, а не
  конвертируется на месте (конвертация может повредить данные старой версии).
- Клавиша экрана журнала — `u`.
- Строки старого формата откатываются только с явным `--root` и без проверки
  принадлежности папке (это ограничение описано в ответе CLI).
- Сбой записи журнала после отката: строка помечается «журнал не записан», код 1,
  автоматического повтора нет (см. алгоритм, пункт 5).
- Идентификатор с микросекундами в метке времени (см. формат).

## Открытые вопросы

1. Старые строки журнала не знают, в какой папке они были. Один `--root` на все
   такие строки может откатить файлы в другой папке, если там есть файлы с теми
   же относительными путями и OSHASH. Проверка OSHASH делает это маловероятным,
   но не исключает. Как поступить: (а) принять риск и предупреждать в выводе;
   (б) требовать подтверждение (`--confirm-legacy`) перед откатом таких строк;
   (в) не откатывать старые строки вовсе, пока пользователь не укажет корень
   для каждой.
