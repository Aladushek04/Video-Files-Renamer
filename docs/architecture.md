## Зачем

Сейчас `clean_ph_names.py` приводит имена к шаблону
`Студия - ДД.ММ.ГГГГ - Актрисы - Название` одними регулярками. На реальной
папке он часто ошибается: путает актрис с названием, режет слова как имена,
оставляет мусор. Примеры из текущего `preview.csv`:

- `Bulgarian Anal - Porn With Adriana Lorenzi...`
- `For Brittany - Andrews Panic Attack...`
- `Yasmina Khan - Manuel Ferrara Finally Got His Hands On Me`

Нужен локальный исправлятор, который сначала пробует найти сам файл в StashDB
и взять оттуда точные студию, дату, исполнителей и название, а эвристику
использует только как запасной вариант. База студий StashDB должна
обновляться скриптом, а не вбиваться руками.

## Цели

- Для каждого видео получить кандидата из StashDB по отпечатку файла (OSHASH),
  затем по текстовому поиску, затем — эвристикой.
- Писать `preview.csv`, который человек просматривает и правит перед
  переименованием.
- Переименовывать только одобренные строки, безопасно и с журналом.
- Скачивать все студии StashDB в `studios.json` для эвристического fallback.
- Работать без обязательных pip-зависимостей: Python 3.14 stdlib + ffprobe при
  необходимости.
- Не отправлять наружу содержимое файлов: только OSHASH и текстовые запросы.

## Не-цели

- Не GUI и не веб-интерфейс в первой версии. TUI — отдельная вторая фаза после
  рабочего CLI (см. ниже).
- Не PHASH и не MD5 целого файла в первой версии. OSHASH дешёвый; PHASH —
  отдельный этап, MD5 на 79 ГБ — слишком дорого.
- Не запись метаданных в контейнер, не скачивание обложек, не интеграция с
  Jellyfin/Stash.
- Не переименование подпапок, субтитров и sidecar-файлов.
- Не автоматическое удаление дублей и не дедупликация сцен.
- Не поиск по актрисам через локальную базу `face-recognition-master`.
- Не изменение поведения старого `clean_ph_names.py` как отдельного CLI, кроме
  общих улучшений, описанных ниже.

## Анти-цели

- Не переименовывать файл, если нет одобренной строки в CSV.
- Не применять эвристику и текстовые совпадения по умолчанию: только
  однозначный отпечаток.
- Не терять прогресс скрапера студий при обрыве.
- Не логировать и не коммитить `STASHDB_API_KEY`.
- Не доверять данным StashDB как безопасным путям: всё санитизируется под
  Windows и проверяется на выход за пределы целевой папки.

## Ограничения

- Windows 10/11, Python 3.14, ffmpeg/ffprobe 9 доступны.
- StashDB GraphQL: `https://stashdb.org/graphql`, заголовок `ApiKey`, не Bearer.
- `findScenesBySceneFingerprints` принимает не более 40 сцен за запрос.
- `queryStudios` пагинируется; имена студий должны быть уникальны, но после
  нормализации ключа возможны коллизии.
- OSHASH: `size + сумма little-endian uint64 первых и последних 64 КБ`,
  16 hex-символов. Точная совместимость со Stash обязательна.
- CSV открывается в Excel: UTF-8 BOM, разделитель `;`.
- В проекте нет git; «коммит» из старых планов заменяется записью файлов и
  тестами.

## Подходы

Рассматривались три варианта:

1. **CLI + CSV-ревью (выбран).** OSHASH → батч-поиск сцены → текстовый поиск →
   эвристика. Результат в CSV, применение только после ревью.
2. CLI + локальный веб-ревью на FastAPI. Удобнее выбирать кандидатов, но это
   новый сервис и фронт, работы в 2–3 раза больше.
3. Только текстовый поиск, без чтения файлов. Проще, но меньше точности и
   больше ложных совпадений.

Выбран вариант 1: он даёт максимум точности на существующей папке, не требует
нового сервиса и оставляет человеку контроль над спорными случаями.

## Как это работает

### Общий поток

1. `scrape_studios.py --apply` обновляет `studios.json` (можно делать редко).
2. `fix_video_titles.py preview D:\Videos\PH` обходит файлы, считает OSHASH,
   ищет сцены, формирует новые имена и пишет `preview.csv`.
3. Человек открывает CSV, проверяет `approved`, при необходимости правит `new`.
4. `fix_video_titles.py apply preview.csv --root D:\Videos\PH --apply`
   переименовывает только строки с `approved=y`, пишет `rename_log.csv`.

### 1. Отпечаток файла

Для каждого регулярного видеофайла считается OSHASH. Читаются только первые и
последние 64 КБ; полный файл не читается. Файлы меньше 8 байт пропускаются.

Отпечатки отправляются батчами до 40 штук:

```graphql
query FindScenesByFingerprints($fingerprints: [[FingerprintQueryInput!]!]!) {
  findScenesBySceneFingerprints(fingerprints: $fingerprints) {
    id
    title
    release_date
    code
    duration
    studio { id name parent { id name } }
    performers { as performer { id name } }
  }
}
```

Переменные: `{"fingerprints": [[{"hash": "...", "algorithm": "OSHASH"}], ...]}`.

Ответ выровнен по порядку входных групп. Если для файла найдена одна сцена —
это точное совпадение, `confidence=1.0`. Автоматически (`approved=y`) оно
одобряется только при валидном итоговом имени: непустой stem и хотя бы один
блок «название» или два других непустых блока. Если сцена пустая или имени не
получилось, строка уходит в fallback/`unchanged` с `approved=n`. Если найдено
несколько сцен — все кандидаты перечисляются в `note`, `approved=n`.

### 2. Текстовый поиск

Если отпечаток не дал результата, из имени убираются студия, дата и техмусор,
остаток нормализуется и отправляется в:

```graphql
query SearchScenes($term: String!, $limit: Int!) {
  searchScene(term: $term, limit: $limit) {
    id
    title
    release_date
    code
    studio { id name parent { id name } }
    performers { as performer { id name } }
  }
}
```

`limit=10`. Запрос один на файл, с паузой между запросами. `--no-text`
отключает этот этап, `--offline` не делает сетевых запросов вообще.

### 3. Скоринг текстового кандидата

Сравниваются нормализованные строки (lowercase, NFKD, без диакритики,
пунктуация → пробелы):

- `title_sim` — максимум из `difflib.SequenceMatcher.ratio()` и Jaccard по
  токенам между локальным остатком и `title` кандидата;
- `performer_hit` — доля исполнителей кандидата, чьё полное имя встречается в
  локальном имени; `as` используется как отображаемое имя;
- `studio_hit` — 1, если нормализованная студия кандидата встречается в
  локальном имени или совпала с распознанной студией;
- `date_hit` — 1 при полном совпадении даты, 0.5 при совпадении года.

Базовая формула: `0.55*title + 0.25*performers + 0.10*studio + 0.10*date`.
Недоступные сигналы (нет исполнителей у кандидата, нет локальной даты)
выбрасываются, веса оставшихся перенормируются.

Правила приёмки:

- кандидат показывается, если `score >= 0.70`;
- лучший кандидат используется, если `score >= 0.85` и выполнено хотя бы одно:
  `performer_hit >= 0.5` или `title_sim >= 0.90`;
- если два кандидата отличаются меньше чем на 0.05, ставится `ambiguous`,
  `approved=n`;
- иначе — эвристический fallback.

Точные веса и пороги — на усмотрение строителя; значения выше — стартовые.

### 4. Fallback

Если StashDB не дал уверенного совпадения, вызывается существующий
`clean_ph_names.clean_stem()` с обновлённым словарём студий. Результат
помечается `source=heuristic`, `approved=n`. Если очистка ничего не изменила,
строка помечается `unchanged` и тоже не одобряется.

Для fallback действуют два улучшения:

- `extract_studio` ищет самый длинный префикс из 1–5 токенов, а не только первый
  токен. Это нужно для `Hussie Pass`, `Brazzers Exxtra` и т.п. Ключи короче 4
  символов не используются, чтобы не ловить обычные слова.
- итоговое имя санитизируется под Windows (см. ниже).

### 5. Формат имени

Для найденной сцены:

```
Студия - ДД.ММ.ГГГГ - Исполнитель 1, Исполнитель 2 - Название
```

Правила:

- студия — `scene.studio.name`; если её нет, распознанная локальная студия; если
  нет и её — блок пропускается;
- дата — `release_date`; если её нет — устаревшее поле `date`; если нет и его —
  локальная дата; если нет и её — блок пропускается;
- исполнители — имена из `performers[].as`, иначе `performer.name`, в порядке
  StashDB; если пусто — блок пропускается, актёры не угадываются;
- название — `scene.title` как есть; если пусто — очищенный локальный остаток;
- официальные строки StashDB не переделываются в Title Case;
- частичная дата: `ГГГГ-ММ` → `ММ.ГГГГ`, `ГГГГ` → `ГГГГ`;
- расширение файла сохраняется байт-в-байт;
- итоговая длина ≤ 255 символов с расширением, обрезка по базе, как в текущем
  `_cap_length`.

Санитизация Windows: `\ / : * ? " < > |` и управляющие символы заменяются на
пробел или дефис, пробелы схлопываются, хвостовые точки и пробелы срезаются,
зарезервированные имена (`CON`, `PRN`, `AUX`, `NUL`, `COM1`–`COM9`,
`LPT1`–`LPT9`) получают префикс `_`. Unicode сохраняется.

### 6. CSV-ревью

`preview.csv`, разделитель `;`, кодировка `utf-8-sig`:

```
approved;old;new;source;confidence;scene_id;note;oshash;size
```

- `old` и `new` — пути относительно `--root`;
- одна строка = один файл; лучший кандидат идёт в `new`/`scene_id`, остальные
  кандидаты и причина — в `note`;
- `source`: `fingerprint`, `phash`, `text`, `heuristic`, `unchanged`;
- `approved`: `y` только для однозначного отпечатка с валидным итоговым именем;
  всё остальное `n`;
- `note` — причина, кандидаты, предупреждения;
- `oshash` и `size` — для проверки актуальности при apply.

Excel-инъекция: если `new` начинается с `=`, `+`, `-` или `@`, в CSV пишется
апостроф перед значением; при apply один ведущий апостроф снимается.

`preview` заранее разрешает коллизии: и внутри партии, и с уже существующими
файлами. Цель, которая сама входит в партию и будет переименована, занятой не
считается. Поэтому `new` в CSV — это финальное имя, а не «примерно такое».
`apply` не добавляет суффикс молча: если цель занята, строка завершается
ошибкой. Исключение — явный флаг `--suffix-collisions`, который разрешает
добавить ` (2)`, `(3)`. Двухфазное переименование снимает проблему цепочек
`A → B, B → C`.

`apply` читает CSV и применяет только `approved` в значениях
`y/yes/1/true` (без учёта регистра). Пустой `approved` = `n`.

Проверки перед переименованием:

- путь `old` существует, это обычный файл, не symlink/junction;
- путь не выходит за `--root` после нормализации;
- `new` непустой, не содержит недопустимых для Windows символов, не является
  зарезервированным именем и не длиннее 255 символов с расширением;
- `new` не содержит подкаталогов и не выходит за `--root`;
- расширение `new` совпадает с расширением `old`;
- если в строке есть `oshash`, он совпадает с текущим (иначе `stale`, пропуск;
  `--force` отключает проверку);
- цель не занята; иначе ошибка строки, если не передан `--suffix-collisions`;
- переименование двухфазное (временное имя → финальное), чтобы не ломать
  регистр и цепочки имён.

Человеческие правки в `new` не санитизируются и не обрезаются молча: строка с
недопустимым именем отклоняется с понятной ошибкой, чтобы применённое имя
всегда совпадало с одобренным. Preview-имена уже санитизированы.

После успеха в `rename_log.csv` добавляется строка
`timestamp;action;undoes;root;old;new;oshash;size;scene_id;source` (с
микросекундами в метке времени). Ошибки по отдельным файлам не останавливают
остальные; итоговый код возврата 1, если были ошибки. Откат записанных строк
описан в `docs/superpowers/specs/2026-11-06-undo-design.md`.

`apply` без `--apply` — dry-run: печатает план, ничего не меняет.

### 7. Кэш

SQLite `cache/title_fixer.sqlite3`, stdlib `sqlite3`. Таблицы:

- `fingerprints(hash TEXT PRIMARY KEY, scenes TEXT NOT NULL, fetched_at TEXT NOT NULL)`
- `text_queries(query TEXT PRIMARY KEY, scenes TEXT NOT NULL, fetched_at TEXT NOT NULL)`

В `scenes` лежит JSON полного ответа StashDB по сцене, а не только ID: так
кэш не зависит от отдельной таблицы сцен и работает офлайн. Отрицательный
результат хранится как `[]`.

TTL: 30 дней, включая отрицательные результаты. `--refresh` игнорирует кэш и
обновляет его. `--offline` читает только кэш; чего нет — идёт в fallback.

Кэш не хранит пути и не мешает переименованию: OSHASH считается заново, поэтому
после rename тот же файл находится по хэшу.

### 8. Студии

`scrape_studios.py` — отдельный скрипт по мотивам уже существующего
`docs/superpowers/plans/2026-11-04-studios-scraper.md`, но без `httpx`:
stdlib `urllib.request`.

Запрос:

```graphql
query Studios($page: Int!, $perPage: Int!) {
  queryStudios(input: {page: $page, per_page: $perPage, sort: NAME, direction: ASC}) {
    count
    studios { id name }
  }
}
```

Поведение:

- ключ только из `STASHDB_API_KEY`; при отсутствии — понятная ошибка;
- 401/403 и GraphQL `not authorized` → сообщение «проверь STASHDB_API_KEY»;
- 429 → `Retry-After`, до 300 с, до 3 попыток; затем ошибка;
- 5xx/сеть → бэкофф 1/3/9 с;
- пауза 1 с между страницами;
- `--per-page` по умолчанию 100; если API не принимает — 50;
- чекпоинт `studios_checkpoint.json` после каждой страницы; обрыв продолжается
  с той же страницы;
- пустая страница внутри заявленного `count` → ошибка, чекпоинт не двигается;
- dry-run по умолчанию ничего не пишет;
- накопленные студии пишутся в рабочий `studios_raw.json` после каждой
  страницы, чтобы обрыв не терял уже полученные имена; итоговый
  `studios.json` собирается при завершении;
- `--apply` делает бэкап `studios.json.bak` и атомарную запись;
- слияние с существующим `studios.json`: ручные записи не затираются;
- коллизии нормализованных ключей: первый по порядку API остаётся, остальные
  пишутся в `studios_collisions.json`;
- `--reset` сбрасывает только чекпоинт, не JSON;
- `--max-pages N` для проверки.

Нормализация ключа — та же, что в `clean_ph_names.py`:
`re.sub(r"[\s._-]+", "", name.lower())`.

### 9. Ошибки, лимиты, секреты

- Клиент: таймаут 30 с, User-Agent `filename-cleaner/1.0`, `Content-Type:
  application/json`.
- GraphQL-ошибки разбираются: `not authorized` → auth, иначе запросная ошибка
  с текстом.
- Ключ никогда не печатается и не пишется в CSV/логи. В `.env` не требуется;
  достаточно переменной окружения.
- Если ключа нет, `preview` работает в режиме `offline` (кэш + эвристика) и
  предупреждает; `scrape_studios` без ключа завершается ошибкой.
- Неверный ключ (401/403 или GraphQL `not authorized`) — фатальная ошибка
  preview: CSV не пишется, чтобы не выглядеть как полноценный результат.
- Временная ошибка сети, 429 после ретраев или сбой одного батча — не роняет
  весь прогон: затронутые файлы помечаются `source=heuristic`/`offline`,
  `note=stashdb_error`, `approved=n`; остальные обрабатываются. Итоговый код
  возврата 1, чтобы сбой не остался незамеченным.
- Сетевые данные StashDB считаются недоверенными: санитизация, проверка длины,
  запрет path traversal.

## CLI

```text
python scrape_studios.py [--out studios.json] [--checkpoint studios_checkpoint.json]
                         [--per-page 100] [--delay 1.0] [--max-pages N]
                         [--apply] [--reset]

python fix_video_titles.py preview D:\Videos\PH [--csv preview.csv]
                               [--recursive] [--limit N] [--no-text]
                               [--offline] [--refresh] [--studios studios.json]

python fix_video_titles.py apply preview.csv --root D:\Videos\PH [--apply]
                             [--log rename_log.csv] [--force]
                             [--suffix-collisions]
```

`preview` по умолчанию не пишет ничего, кроме CSV. `apply` по умолчанию
dry-run. `--limit` нужен для первых N файлов и ручной проверки.

## Структура файлов

Новые плоские модули рядом с существующими (стиль проекта — плоские скрипты):

```text
oshash.py             # точный OSHASH
stashdb_client.py     # GraphQL: сцены, поиск, студии, ретраи, 429
title_cache.py        # SQLite-кэш
title_matcher.py      # нормализация, скоринг, сборка имени из сцены
title_service.py      # сервисный слой: preview/apply без печати в stdout
fix_video_titles.py   # тонкий CLI-адаптер над title_service
scrape_studios.py     # CLI скрапера студий
tests/test_oshash.py
tests/test_stashdb_client.py
tests/test_title_matcher.py
tests/test_title_cache.py
tests/test_fix_video_titles.py
tests/test_scrape_studios.py
```

`clean_ph_names.py` остаётся точкой входа эвристики; из него переиспользуются
`clean_stem`, `extract_date`, `build_new_name`, `_cap_length`. Общие изменения:
длинный префикс студии и Windows-санитизация.

`title_service.py` — единственная точка входа для CLI и будущего TUI. Он
возвращает dataclasses (`PreviewRow`, `ApplyReport`, `ProgressEvent`) и не
печатает в stdout, не читает CSV и не знает про argparse. CLI отвечает за
аргументы, CSV и печать; TUI — за экран. Это требование к структуре, чтобы TUI
не пришлось переписывать логику.

## Тесты

- OSHASH на векторах из Go-тестов Stash: `hello world` →
  `d3e392dee38cd4df`, `this is a test` ×15 → `6a0eba04654d0b9b`, хвостовые
  кейсы → `d5d6ddd820756920`, пустой/<8 байт → ошибка.
- GraphQL-клиент: успешный батч, выравнивание ответа, 401/403, 429,
  GraphQL-ошибка, таймаут, пагинация студий, чекпоинт.
- Матчер: уникальный отпечаток, несколько сцен, текстовый кандидат выше/ниже
  порога, `as`-алиас, пустая студия/дата/исполнители, частичная дата.
- Имена: официальный Title Case не ломается, Windows-санитизация, длина,
  Unicode, коллизии, расширение `.MP4`.
- CLI: preview не меняет файлы, apply применяет только `y`, stale-файл
  пропускается, path traversal отклоняется, лог пишется, dry-run apply ничего
  не меняет.
- Безопасность имён: уникальный отпечаток с пустым/неполным итогом не
  автоодобряется; ручная правка с `CON`, `:` или длиной >255 отклоняется;
  занятая цель не получает суффикс без `--suffix-collisions`.
- Ошибки StashDB: неверный ключ не пишет CSV; временный сбой батча даёт
  `stashdb_error` и код возврата 1, но не роняет остальные файлы.
- Живой smoke-тест на `D:\Videos\PH` выполняет человек с реальным ключом:
  `preview --limit 5`, затем полный preview, затем apply после ревью.

## Следующая фаза: TUI

TUI не входит в первый релиз, но ядро проектируется под него.

Цель: новый пользователь запускает TUI и без чтения README проходит путь:

1. выбирает папку;
2. вводит `STASHDB_API_KEY` скрытым вводом (или видит, что ключ уже в
   окружении);
3. обновляет студии с прогрессом;
4. запускает preview с прогресс-баром;
5. видит таблицу: файл, текущее имя, предложение, источник, уверенность,
   кандидаты;
6. фильтрует «требует внимания», принимает/отклоняет, выбирает альтернативу;
7. смотрит итоговый diff и подтверждает apply;
8. видит отчёт и путь к `rename_log.csv`.

Требования:

- красивый, но не перегруженный интерфейс: Textual (или другой современный TUI)
  с тёмной темой, клавиатурной навигацией и понятными подсказками;
- те же состояния, что в CLI: пустой кэш, нет ключа, ошибка сети, неверный
  ключ, пустая папка, спорные совпадения;
- вся логика — через `title_service`, без парсинга CSV и вызова subprocess;
- apply только после явного подтверждения; журнал и откат видны;
- TUI-зависимости не обязательны для CLI: ядро остаётся stdlib, TUI ставится
  отдельно (`requirements-tui.txt` или venv);
- дизайн TUI и выбор библиотеки — отдельный brainstorming после приёмки CLI;
  здесь фиксируются только требования и точка интеграции.

## Риски

- OSHASH совпадает только с точной копией файла. Для перекодированных
  tube-файлов совпадения может не быть; выручает текстовый поиск и ревью.
- Текстовый поиск может дать ложное совпадение; поэтому он никогда не
  одобряется автоматически.
- StashDB может не знать конкретную сцену; fallback остаётся эвристическим.
- Полный дамп студий может дать ложные срабатывания на коротких общих словах;
  защита — минимальная длина ключа и самый длинный префикс.
- Ошибка в CSV или устаревший preview может привести к неверному переименованию;
  защита — проверка OSHASH/size и двухфазное переименование.
- 79,5 ГБ не читаются целиком; OSHASH не должен случайно перейти в полный MD5.

## Решения, оставленные строителю

- Точные веса и пороги скоринга (стартовые значения выше).
- Размер страницы студий (100 или 50) после проверки живым запросом.
- Конкретная схема SQLite и TTL (в дизайне предложены).
- Точная карта санитизации Windows и поведение зарезервированных имён.
- Наличие флага `--auto-approve-text` (предложение: добавить, по умолчанию
  выключен).
- Формат `studios_collisions.json` и степень детализации `note`.
- Нужно ли обновлять старый план `2026-11-04-studios-scraper.md` или заменить
  его новым планом (предложение: заменить новым, старый оставить как историю).
